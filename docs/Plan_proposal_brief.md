### 1.3 설계 원칙 — 문서에 적혀 있는 것 (CLAUDE.md "설계 원칙")

- **3계층 분리: 원장 / 렌즈 / 화면.** 원장은 판단 없이 넓게, 렌즈는 프롬프트·규칙으로 좁게, 화면은 즉시 변경.

  섹터 전환(주거 → 오피스)은 SYSTEM_PROMPT 한 블록 교체로 가능하도록 남겨둔 비대칭 결정.

- **쓰기 순서 규칙** — 영속 저장소 먼저, 그 다음 작업본, 마지막 commit. 반대면 "이미 처리됨"만 남고 내용은 잃는다.

## 2. [공통] 초안

### 1절 한 줄 요약 (후보)

**5절 공통 주장 문장 — 두 앱에 다 참인 것으로 (2026-10-23 조정)**

> **AI의 판단과 코드의 판정을 섞지 않는다 — 무엇이 AI이고 무엇이 계산인지, 사람이 항상 구분할 수 있게.**

- IC Helper: 판정을 LLM에서 결정론으로 옮기고 LLM은 서술만. 근거 — LLM 판정 vs 결정론 일치율 52.2%(IC CLAUDE.md:243, 커밋 9d8c1ee~c284444; **범주 분포 병기 필요** — 아래 §6)
- The Brief: LLM 관련성(woomi_relevance)과 Python 공급 판정을 합산하지 않고 나란히(교차표 독립)
- IC 세션 제안 "AI에게 판단을 맡기지 않고, 판단에 필요한 것을 사람 앞에 펼쳐놓는다"는 The Brief에선 반만 참(관련성·카테고리는 LLM이 판단) → 위 문장으로 대체 제안. "판정이 아니라 추적"은 IC 6절 사례 제목으로

> **AI가 낸 숫자와 문장마다, 어디서 왔고 무엇이 빠졌는지를 사람이 따라갈 수 있게 만든 두 도구 —
> 시장을 읽는 The Brief, 딜을 뜯는 IC Helper.**

대안(짧게): "판정은 코드가, 서술은 AI가 — 그리고 모르면 모른다고 적는 두 도구."

| IC Helper | 딜 단위 언더라이팅 | OM·재무모델·CoStar·Seed | 스크리닝, RLV, 조정표, IC 검증 |

한 문단: 시장을 읽는 눈과 딜을 뜯는 눈은 다른 도구다. 둘을 합치지 않고 역할을 나눴다. 연결은 **데이터**로 —
The Brief가 만든 지역별 공급 판정(`context_latest.json`)을 IC Helper가 딜 지역 조회에 쓰는 것이 다음 단계다(계획, §1.9-4).

### 9절 만든 방법 — The Brief 쪽에서 보태는 항목

- research → Plan → 리뷰 → 구현, 단계마다 독립 커밋·검증·보고 후 다음 (Plan_market §7 체크리스트가 그 기록)
- 불변조건을 먼저 적고 코드를 쓴다 — M1~M9 (Plan_market §0, CLAUDE.md)
- 임계값·실행 시각 같은 "정하는 값"은 감이 아니라 측정 분포로 (research_market §12.4, Plan_market §7)
- LLM 출력은 Python이 사후검사한다 — 통과 못 하면 로그에 남기고 사람이 본다 (CLAUDE.md "Phase 6")
- 실패는 문서에 남긴다 — 142건 중복·Manhattan 116건·라벨 유출 2문장 (CLAUDE.md, contest_evidence.md)

맺음(IC outline 9절과 같은 문장): AI로 개발 속도는 올라가지만 틀린 것이 조용히 섞이는 속도도 같이 올라간다.
그래서 기능보다 검증 장치에 먼저 공을 들였다.
